# FlowNote 연구 결과 정리

## 문서 기준

- 기준일: 2026-08-13
- 대상: 현재 저장소에 구현된 FastAPI 서버, Windows WPF 앱, Android 앱과 보존된 검증 기록
- 제품 단계: 공개 가능한 현재 기준선을 정리한 연구개발 프로토타입

이 문서는 FlowNote 연구의 목적, 구현 결과, 검증 범위와 남은 과제를 한 번에 검토할 수 있도록 정리한 현재 기준 보고서다. 이후 UX가 바뀌면 화면별 사용법은 역할별 매뉴얼에서 갱신하고, 연구 목적과 핵심 데이터 원칙은 제품·설계 문서에서 관리한다.

## 1. 연구 요약

FlowNote는 생산현장의 문서와 현장 경험을 추적 가능한 하나의 흐름으로 연결하는 온프레미스 시스템을 연구한다. 기존 문서관리 시스템이 파일과 버전을 중심으로 다루는 데 비해, FlowNote는 문서가 실제 작업에 사용된 맥락, 작업 중 발생한 짧은 기록, 사진, 인수인계, 관리자 판단과 보고서 근거까지 함께 보존한다.

핵심 연구 가설은 다음과 같다.

> 현장 문서와 작업자의 경험을 같은 권한·감사·원천 추적 체계에서 축적하면, 특정 담당자에게 묶인 암묵지를 조직의 재사용 가능한 근거 데이터로 전환할 수 있다.

연구 결과, 문서의 검토·공개, FieldComment의 불변 원천, 작업순서·인수인계, 보고서 원천 고정, 연결 불안정 구간의 로컬 보존과 재시도, 설치형 클라이언트 접근 통제, AI ground-truth 준비 구조를 서버와 두 종류의 클라이언트에 구현했다.

현재 결과는 운영 완제품 판정이 아니다. 운영 배포는 연구개발 완료 범위에서 제외하며, Windows x64 통합 기준선, 승인 Android 실단말, 코드 서명·MDM, 고객 유사망, 별도 PC 복구와 제한 파일럿은 실제 도입을 결정할 때 별도로 수행한다.

## 2. 연구 배경

생산현장에서는 문서가 존재해도 실제 업무의 판단 근거가 충분히 남지 않는 경우가 많다.

1. 파일 서버에는 여러 문서가 있지만 현장에서 사용해야 할 공개본이 분명하지 않다.
2. 설비 상태, 품질 이상, 재작업 판단과 숙련자의 대응은 구두 전달에 의존하기 쉽다.
3. 현장 코멘트를 보고서로 정리하면서 원문, 사진과 관리자 판단의 연결이 끊긴다.
4. 연결이 불안정하면 현장 입력이 유실되거나 같은 요청이 중복 처리될 수 있다.
5. 권한과 출처가 정리되지 않은 데이터는 AI 검색과 의사결정 보조의 근거로 사용하기 어렵다.

FlowNote는 DMS와 KMS 중 하나만 선택하지 않는다. 문서의 버전·공개·열람 이력과 현장의 짧은 경험 기록을 연결하고, 원천 기록과 정제 보고서를 함께 보존하는 구조를 연구 범위로 삼았다.

## 3. 연구 목표와 범위

### 3.1 목표

- 문서의 최신 업로드와 현장 공개본을 분리한다.
- 현장 기록을 삭제·덮어쓰기 어려운 원천으로 보존한다.
- 작업순서, 문서, FieldComment, 인수인계와 보고서 사이의 출처를 추적한다.
- 네트워크 장애와 재시도에서도 원천 유실과 중복을 막는다.
- 서버, Windows와 Android에서 역할·단말 기반 접근을 통제한다.
- 외부 AI 호출보다 먼저 검색 근거의 품질·권한·승인 구조를 준비한다.

### 3.2 초기 범위

- 사내 서버 PC 한 대의 FastAPI와 SQLite
- 관리자·현장 PC용 Windows WPF 설치형 앱
- 승인 태블릿·러기드 단말용 Android 설치형 앱
- 서버 로컬 `storage/` 파일 저장
- 관리자가 입력하는 초기 작업순서
- 문서, FieldComment, 사진, 채널 알림, 인수인계와 보고서

### 3.3 제외·후속 범위

- MES/ERP 대체
- 일반 브라우저 직접 사용자 접근
- 개인 휴대폰 기본 배포
- GPS·근태 관리와 개인 메신저 수집
- 실제 외부 AI provider 운영 연동
- 현장별 MES/ERP 어댑터
- 클라우드 기본 운영

## 4. 연구 방법

FlowNote는 다음 순환 구조로 연구를 진행한다.

```mermaid
flowchart LR
    O["현장 문제·관찰"] --> M["문서·업무 모델링"]
    M --> I["서버·클라이언트 구현"]
    I --> V["단위·회귀·스모크 검증"]
    V --> P["파일럿·역할별 관찰"]
    P --> D["수용·불수용·추가 검토"]
    D --> M
```

현재까지는 코드·계약·보존 정책을 중심으로 한 내부 기술 검증을 수행했고, 제한 현장 파일럿은 승인과 실기 증거가 준비될 때까지 대기 상태로 유지했다. 현장 의견은 즉시 기능으로 흡수하지 않고 `수용`, `불수용`, `추가 검토`로 구분해 제품 범위와 데이터 추적성에 미치는 영향을 함께 판단한다.

## 5. 시스템 구성

### 5.1 FastAPI 서버

서버는 다음 권위 원천을 관리한다.

- 서버 계정, 역할, 세션과 승인 단말
- 문서, 버전, 공개 포인터와 승인 이력
- 문서 접근 로그와 controlled copy
- FieldComment, 첨부, 검토와 품질 집계
- 작업순서, 채널 메시지, 알림 cursor와 인수인계
- 보고서, 원천 snapshot과 정정 계열
- AI 검색 후보, ground-truth, 평가와 운영 안전장치
- mutation receipt, 공통 감사와 서버 재결합 상태

서버 PC 한 대는 고객 하나와 현장 하나의 경계로 운영한다. 다른 scope 요청은 대상 존재 여부를 드러내지 않도록 거부한다.

### 5.2 Windows WPF 앱

Windows는 관리와 문서 운영의 중심 클라이언트다.

- 서버 계정 로그인과 비밀번호 변경
- 폴더·문서 등록, 버전, 태그와 상태 조회
- 문서 검토·공개 승인 작업함
- 파일 감시와 변경 후보 처리
- FieldComment 검토·품질·역추적
- 작업판, 현황판과 작업순서 전달
- 채널·알림·인수인계 확인 현황
- 보고서 초안, 원천 검증, 확정과 정정
- 계정·승인 단말·AI 운영 관리

로컬 SQLite와 `Files`는 연결 불안정 구간의 업무 원천과 동기화 상태를 보존한다. 서버 권위 데이터와 자동으로 충돌을 덮어쓰지 않는다.

### 5.3 Android 앱

Android는 승인된 현장 단말의 짧은 업무 흐름에 집중한다.

- 승인 단말 ID를 포함한 서버 로그인
- 공개 문서 목록·상세와 앱 내부 보안 열람
- 오늘의 작업순서 조회
- FieldComment, 신호등식 상태와 사진
- 채널 알림 조회와 읽음 처리
- 인수인계 작성·확인·보류와 후속 FieldComment

FieldComment, 사진과 인수인계는 전송 전에 Android Keystore 기반 암호화 outbox에 보존한다. 서버 저장 뒤 사진이나 알림만 실패한 부분 성공도 같은 원천 ID를 유지하고 실패 단계만 재시도한다.

## 6. 주요 구현 결과

### 6.1 문서 공개의 책임 분리

문서 등록은 즉시 공개가 아니다. 등록 문서는 `WORKING` 상태가 되고, 검토 요청은 최신 version·revision·file hash를 고정한다. 승인된 정확한 버전만 공개할 수 있어 업로드 시점의 최신 파일과 현장 사용 확정본을 구분한다.

### 6.2 현장 원천과 관리자 해석의 분리

FieldComment의 본문, 신호, 작성자와 원천 연결은 생성 뒤 수정·삭제하지 않는 원천으로 취급한다. 담당자, 기한, 분석, 검토 상태와 보고서 선정은 별도 이력으로 보존한다. 적색 신호나 상충 기록은 분석자와 결정자를 분리할 수 있다.

### 6.3 보고서 근거의 고정

보고서 초안과 최종 저장은 서로 다른 원천 유형을 요구한다. 선택한 FieldComment, 공개 문서와 작업순서 이력은 version·revision·hash로 고정하며 저장 직전에 서버에서 다시 확인한다. 확정 뒤 정정이 필요하면 원본을 덮어쓰지 않고 독립 정정본을 재검토한다.

### 6.4 연결 장애에서의 무손실 처리

Windows는 로컬 저장과 동기화 큐, Android는 암호화 outbox를 사용한다. idempotency key와 mutation receipt로 응답 유실 뒤 재시도의 중복 생성을 줄이고, stale revision은 자동 덮어쓰지 않는다. 서버 복구나 교체로 instance·epoch·cursor가 역행하면 자동 전송을 차단하고 관리자가 재결합을 승인한다.

### 6.5 설치형 앱의 접근 통제

Windows와 Android는 승인된 HTTPS 서버에 로그인한다. Android는 서버에 등록된 활성 단말만 세션을 받을 수 있다. 문서 본문은 단기 1회 grant로 앱 내부에서만 열며 크기와 SHA-256을 대조한다. 공유와 외부 앱 열기는 제공하지 않고 보안 뷰어에 화면 보호를 적용한다.

### 6.6 AI 근거 준비

외부 AI 호출보다 먼저 다음 구조를 구현했다.

- 원천 DB에서 재생성할 수 있는 검색 후보
- 제외 사유와 품질 지표
- 독립 2인 승인 ground-truth
- 불변 dataset version과 평가 run
- 실제 익명 현장 데이터와 합성·시험 데이터의 분리
- 외부 전송 승인, 민감정보 정책, kill switch, 한도와 보존 정책

현재 외부 호출은 기본 비활성 상태이며, 실제 provider를 사용하는 사용자 화면은 운영 범위가 아니다.

## 8. 연구의 의미

FlowNote의 기술적 의미는 개별 화면 수보다 다음 연결을 실제 데이터 계약으로 구현했다는 데 있다.

1. 문서 파일과 현장 공개 책임을 분리했다.
2. 작업자의 짧은 기록을 관리자 보고서의 추적 가능한 원천으로 연결했다.
3. 네트워크가 불안정해도 업무 원천을 먼저 보존하도록 설계했다.
4. AI 기능에 앞서 출처, 권한, 승인과 회귀 평가 기반을 마련했다.
5. 현장 의견을 제품 범위와 추적성 기준으로 판단할 수 있는 구조를 만들었다.

이 구조는 특정 개인의 기억에 의존하던 경험을 재사용 가능한 조직 데이터로 축적하는 기반이 된다.

## 9. 한계와 위험

### 9.1 현장 사용성 근거 부족

현재 UX는 코드와 내부 검증 기준으로 구현돼 있지만, 여러 역할과 실제 장비 조건에서 반복 측정한 현장 근거가 부족하다. 따라서 화면의 정보 순서와 입력 방식은 향후 개편될 수 있다.

### 9.2 연구 결과와 운영 배포의 경계

코드 서명, MDM, 인증서, 고객 유사망, 실제 백업·복구와 rollback은 현장별 승인값과 장비가 필요하다. 이 연구에서는 재현 방법과 확인 항목까지 기록하고 실제 운영 승인과 증거 수집은 도입 조직의 후속 범위로 둔다.

### 9.3 SQLite 운영 경계

초기에는 서버 PC 한 대와 SQLite를 사용한다. 쓰기 경합과 백업·복구 기준을 마련했지만, 현장 규모와 동시성 요구가 커지면 PostgreSQL 전환을 검토해야 한다.

### 9.4 AI 운영 범위

ground-truth와 안전장치는 구현됐지만 실제 provider의 품질·비용·개인정보·보존 정책을 현장에서 검증하지 않았다. AI 운영을 현재 연구 완료 범위로 주장하지 않는다.

## 10. 다음 연구 단계

1. 현재 UX 기준으로 역할별 업무 시나리오와 매뉴얼을 유지한다.
2. 역할별 사용자를 관찰해 UX 변경 전 기준을 측정한다.
3. 수용한 P0·P1 개선은 같은 조건에서 변경 전후를 다시 측정한다.
4. 충분한 익명 현장 데이터와 승인이 쌓인 뒤 AI provider 연구 착수를 별도로 심사한다.
5. 실제 도입을 결정한 조직은 Windows x64, 승인 Android 실단말, 고객 유사망, 복구와 rollback 검증을 배포 문서에 따라 별도로 수행한다.

## 11. 현재 시점의 완료 정의

### 문서 정리 완료

- GitHub README에서 목적, 구조, 현재 상태와 제한을 이해할 수 있다.
- 연구 결과, 설계, 역할별 매뉴얼과 검증 기록이 독자별로 연결된다.
- 현재 메뉴와 업무 절차가 실제 코드와 일치한다.
- 연구개발 완료와 실제 운영 도입 조건이 명확히 구분된다.

### 연구 프로토타입 구현 완료

- 현재 저장소에 구현된 서버·Windows·Android 기능과 계약이 관련 테스트를 통과한다.
- 실패·보류·미검증 범위를 숨기지 않고 기록한다.

### 오픈소스 공개 준비 완료

- 공개 작업 트리에 실제 고객·운영 데이터, 비밀값, 개인 경로와 생성 산출물이 없다.
- 공개 예시값과 `.gitignore` 경계가 적용돼 있다.
- 현재 공개 브랜치 이력과 의존성 보안 상태를 별도로 점검한다.

운영 배포는 연구개발 완료 정의에 포함하지 않는다. 필요한 방법과 검증 절차는 [배포 기준](./deployment.md)에 참고 절차로 남긴다.
