# 역할별 업무 UX와 접근성 공통 기준

이 문서는 FlowNote Windows WPF 클라이언트와 Android 현장 단말에 공통으로 적용할 UX·접근성 기준을 정한다. 자동 테스트나 코드 반영 여부와 현장 사용성 통과 여부는 구분한다. 현장 통과는 승인된 같은 장비·망·단말 위치에서 같은 참여자가 수행한 BEFORE/AFTER 증거로만 판단한다.

## 1. 핵심 업무와 정보 순서

역할별 비교 업무는 다음 세 흐름을 기준으로 한다.

1. 문서 찾기 → 열람 → FieldComment 저장과 보존·동기화 상태 확인
2. 인수인계 수신·확인 → 후속 FieldComment 생성과 원천 연결 확인
3. FieldComment 검토 → 보고서 근거 선정, 또는 비관리자의 정상적인 권한 부족 확인

첫 화면에는 현재 역할이 자주 수행하는 업무와 처리할 항목을 먼저 보여준다. 화면 이동을 줄이더라도 역할 검사, 원천 ID·버전·hash·감사 연결, 저장 전 확인, 충돌·부분 성공 확인은 숨기거나 자동 통과시키지 않는다.

오류와 권한 부족 안내는 아래 순서를 유지한다.

1. 무엇이 실패했는지
2. 무엇이 서버 또는 단말에 보존됐는지
3. 누가 처리해야 하는지
4. 사용자가 지금 할 수 있는 일

비관리자의 검토·보고서 권한 부족은 기능 장애로 표시하지 않는다. 원천 FieldComment와 기존 이력이 변경·삭제되지 않았음을 알리고 현장 관리자에게 로그인 ID와 필요한 역할·채널 권한을 요청하도록 안내한다. 로컬 권한 우회, 원천 덮어쓰기, 확인 단계 생략은 이동 수 감소로 인정하지 않는다.

## 2. 입력과 이동

- 주요 버튼은 화면마다 같은 의미와 상대적 위치를 유지한다. 파괴적이거나 되돌리기 어려운 동작은 기본 초점이나 기본 버튼으로 두지 않는다.
- 입력 기본값은 현재 역할·업무·선택한 원천에서 안전하게 확정할 수 있는 값만 사용한다. 담당자, 공개 상태, 보고서 근거, 인수인계 수신자처럼 책임이나 공개 범위를 바꾸는 값은 사용자가 확인한다.
- 저장 뒤에는 저장된 원천 ID, 서버 접수 여부, 단말 보존 여부와 다음 확인 위치를 함께 표시한다. 부분 성공에서는 성공 항목을 다시 보내지 않고 실패·충돌 항목만 다시 선택하게 한다.
- 단절 뒤 재개할 때 작성 중 입력과 전송 대기 항목을 보존한다. 자동 재개 또는 재전송 여부, 중복 방지 식별자와 마지막 결과를 사용자가 확인할 수 있어야 한다.
- 오류 문구는 내부 예외, 파일 경로, 토큰 또는 고객 원문을 노출하지 않고 사용자가 실행할 수 있는 다음 행동을 한글로 설명한다.

## 3. 키보드와 초점

- Windows의 초점 순서는 화면의 시각적 읽기 순서와 일치해야 하며 제목·필터·목록·상세·주요 실행·취소 순으로 이동한다. Android의 외부 키보드와 접근성 탐색 순서도 같은 정보 순서를 따른다.
- Tab과 Shift+Tab으로 모든 입력·선택·실행 요소에 도달하고 원래 위치로 돌아올 수 있어야 한다. 모달, 목록, 표, 날짜 선택기와 미리보기 안에 초점이 갇히면 안 된다.
- 현재 초점은 고대비 모드에서도 식별 가능한 테두리나 모양으로 표시한다. 색 변화만으로 초점을 표시하지 않는다.
- Enter·Space·Escape 같은 기본 키는 플랫폼 관례와 일치시킨다. 키보드만으로 권한 확인, 저장 전 확인과 오류 상세를 건너뛸 수 없게 한다.
- 비활성 요소는 비활성 이유와 필요한 권한 또는 선행 조건을 인접 안내나 접근성 이름으로 제공한다.

## 4. 고대비·색각·글꼴 확대

- 상태와 신호등식 기록은 색상만으로 구분하지 않는다. 상태명, 형태가 다른 아이콘, 건수 또는 짧은 설명을 함께 표시한다.
- 텍스트와 주요 경계는 운영체제 고대비 테마에서 사라지지 않아야 한다. 배경 이미지나 고정 색상 위에만 의미 있는 텍스트를 놓지 않는다.
- Windows 200% 표시 배율과 Android 200% 글꼴 크기에서 핵심 문구가 잘리거나 버튼·입력란이 겹치면 안 된다. 가로 스크롤만으로 핵심 업무를 완료하게 하지 않는다.
- 확대 상태에서도 권한, 원천 보존, 담당자, 다음 행동 문구의 전체 내용에 접근할 수 있어야 한다. 말줄임표를 사용하면 접근성 이름, 툴팁 또는 펼치기로 전체 문구를 제공한다.

## 5. 터치·장갑·한 손·거치 조건

- Android 터치 목표는 최소 48×48dp, 현장 주요 실행 버튼과 수신자 선택은 최소 높이 56dp를 사용한다. Windows에서 터치 사용을 허용한 실행·선택 요소는 최소 44×44DIP를 확보한다.
- 인접한 파괴적 동작과 주요 저장 동작 사이에는 오터치를 막을 간격을 둔다. 작은 아이콘만으로 필수 업무를 실행하지 않는다.
- 장갑 조건에서는 스와이프, 길게 누르기, 정밀 드래그를 필수 동작으로 사용하지 않는다. 동일 기능을 명확한 단일 탭 또는 키보드 동작으로 제공한다.
- 한 손 사용과 고정 거치 조건에서는 자주 쓰는 조회·저장·확인 동작을 반복적인 화면 상하 왕복 없이 수행할 수 있게 한다. 단말 위치 때문에 가려지는 하단 버튼이나 화면 가장자리 전용 제스처에 의존하지 않는다.
- 장갑, 한 손, 거치 위치의 적합성은 치수만으로 통과 처리하지 않는다. 승인 단말과 실제 위치에서 터치 성공, 오입력, 도움 요청과 작업 중단을 관찰한다.

## 6. BEFORE/AFTER 측정과 수용 기준

각 관리자·반장·조장·작업자는 역할별 세 흐름을 같은 참여자, 역할, 시나리오, 승인 테스트 원천, 장비, 망, 단말 위치와 조건에서 BEFORE 2회와 AFTER 2회 수행한다. 연결/단절, 장갑 착용/미착용, 한 손/양손과 실제 거치 위치를 `condition_id`로 고정하고 다른 조건의 결과를 한 비교로 합치지 않는다.

각 시도에는 완료 시간, 선택 수, 화면 이동, 재시도, 도움 요청, 오입력, 권한 부족 이해, 단절 뒤 재개, 원천·처리 결과 유실, 중복 생성, 치명적 blocker, 화면 증거, 서버 원천 ID와 감사 증거를 남긴다. `role-ux-comparison.csv`와 `development-items.csv`는 수용한 P0/P1을 같은 `comparison_id`와 `development_cycle_id`로 연결한다.

수용한 P0는 전부 `VERIFIED` 또는 `CLOSED` 상태여야 하고 AFTER의 치명적 blocker, 원천 유실, 처리 결과 유실과 중복 생성은 모두 0이어야 한다. 중앙 완료 시간·화면 이동·도움 요청 중 하나 이상은 개선되고 세 지표와 중앙 재시도 수의 나머지 값은 악화되지 않아야 한다. 권한 부족 시나리오의 AFTER 참여자는 원천이 보존됐다는 사실과 요청할 현장 관리자를 모두 정확히 설명해야 한다.

현재 보존된 실제 파일럿 자료에는 이 기준을 충족하는 역할별 BEFORE 행과 수용 P0/P1 연결, 동일 조건 AFTER 2회가 없다. 따라서 이 문서는 공통 설계·측정 기준이며 현장 UX PASS 증거가 아니다.

## 7. 운영 준비도 화면

WPF `운영 준비도`는 변경 이력과 합치지 않고 별도 창으로 둔다. 정보 순서는 전체 차단·주의 수와 snapshot 기준 → 영역별 상태 → 조치 목록 → 선택 상세와 기존 업무 화면 이동 → 별도 AI 실제 현장 준비도다. 상태는 색상만 사용하지 않고 `✓/⚠/⛔/?` 아이콘, `정상/주의/차단/집계 없음` 한글명과 건수를 함께 표시한다.

영역 표와 조치 표는 화면 읽기용 한글 이름, 키보드 행 선택과 열 정렬을 제공한다. 긴 대상명·담당 역할·다음 행동·오류 문구는 상세 영역에서 줄바꿈과 세로 스크롤로 전체 확인할 수 있어야 한다. 200% 표시 배율에서는 창 최소 크기만으로 통과 처리하지 않고 필터, 두 표, 상세, 이동 버튼과 AI 분리 안내에 키보드로 도달하고 전체 문구를 읽을 수 있는지 실제 Windows에서 확인한다.

집계 실패는 실패 영역, 원천 보존, 담당 역할, 다음 행동을 분리하고 다른 영역을 숨기지 않는다. 권한 부족은 필요한 역할과 시스템 관리자 문의 방법을 안내하지만 숨긴 채널·대상이나 제외 건수를 노출하지 않는다. `refreshRequired`가 참이면 기존 snapshot을 유지한다는 사실과 기준 시각을 알리고 사용자가 새로고침을 선택하게 한다. 조치 이동은 자동 해결이 아니며 열린 기존 업무 화면에서 다시 권한과 현재 revision을 확인한다.
