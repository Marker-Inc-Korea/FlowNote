# FlowNote 공통 장애 대응

## 1. 기본 대응 순서

장애가 발생하면 아래 순서로 확인한다.

1. 화면에 표시된 실패 내용과 오류 코드를 기록한다.
2. 보존된 데이터가 무엇인지 확인한다.
3. 처리 담당자가 사용자, 현장 관리자, 서버 운영자 중 누구인지 구분한다.
4. 화면이 안내하는 지금 할 수 있는 조치를 수행한다.
5. 원인 해결 뒤 같은 원천 ID·멱등키·동기화 큐로 재개한다.
6. 정상 처리와 서버 read-back을 확인한다.

오류가 생겼다는 이유만으로 로컬 DB, `Files`, Android outbox, 서버 DB, storage나 로그를 삭제하지 않는다.

## 2. 문의할 때 남길 정보

- 발생 시각과 사용자 역할
- Windows PC명 또는 Android 단말 ID
- FlowNote 앱·패키지 버전
- 승인된 서버 주소의 호스트명
- 수행하려던 메뉴와 버튼
- 화면에 표시된 한글 오류 문구와 오류 코드
- 문서 ID, 작업 항목 ID, FieldComment ID 또는 인수인계 ID
- 전송 대기·부분 성공·실패 건수
- 문제가 다시 발생하는지 여부

비밀번호, access token, refresh token, 개인키와 실제 고객 문서 원문은 문의 내용에 포함하지 않는다.

## 4. 서버 연결 실패

### 증상

- Windows 로그인 화면에 서버 연결 실패·timeout 표시
- Android 로그인·문서·알림 조회 실패
- `/health` 또는 `/health/db` 실패

### 확인 순서

1. 다른 사용자도 같은 증상인지 확인한다.
2. 클라이언트의 날짜·시간을 확인한다.
3. 승인된 HTTPS 서버 호스트명이 맞는지 확인한다.
4. 서버 PC 작업 스케줄러 `\FlowNote\FlowNoteApi` 상태를 확인한다.
5. 서버 내부 loopback health를 확인한다.
6. reverse proxy와 인증서 상태를 확인한다.
7. DNS와 방화벽을 확인한다.
8. DB health와 서버 오류 로그를 확인한다.

### 금지

- `http://` 또는 localhost로 클라이언트를 우회하지 않는다.
- 연결 실패 중 로컬 원천·큐·cursor를 지우지 않는다.
- 운영 DB·storage·로그를 개발 PC로 복사하지 않는다.

## 5. HTTPS 인증서 오류

다음 순서로 점검한다.

1. PC·단말 날짜와 시간이 맞는지 확인한다.
2. 접속 호스트명이 인증서 SAN에 포함되는지 확인한다.
3. 인증서 만료일과 폐기 상태를 확인한다.
4. 루트·중간 인증서가 클라이언트에 신뢰 배포됐는지 확인한다.
5. CRL·OCSP 접근이 현장망에서 가능한지 확인한다.
6. 갱신 인증서가 reverse proxy에 실제 적용됐는지 확인한다.

인증서 검사를 끄거나 HTTP로 바꾸지 않는다.

## 6. 로그인 실패

### 401 또는 비밀번호 오류

- 로그인 ID와 키보드 상태를 확인한다.
- 임시 비밀번호를 변경한 계정은 새 비밀번호로 다시 로그인한다.
- 비밀번호 재설정 여부와 세션 폐기 시각을 관리자에게 확인한다.
- Windows가 로컬 계정으로 우회 로그인하지 않는 것이 정상이다.

### 403 또는 권한 오류

- 현재 로그인 역할과 수행하려는 업무를 확인한다.
- 계정 상태가 `ACTIVE`인지 확인한다.
- 필요한 역할을 현장 관리자에게 요청한다.
- 관리자 기능을 수행하려고 계정을 공유하지 않는다.

### Android 승인 단말 오류

- 입력한 `device_id`가 관리자 화면의 값과 정확히 같은지 확인한다.
- 단말 상태가 `ACTIVE`인지 확인한다.
- 교체·비활성·폐기 이력이 있는지 확인한다.
- 새 device ID를 사용하려면 Windows에서 신규 또는 교체 등록한다.

## 7. Windows 문서 등록·동기화 실패

### 등록 직후 서버 실패

1. 하단 상태에서 로컬 DB 저장 성공 여부를 확인한다.
2. `현장 운영 > 로컬 이력`에서 전송 대기 또는 실패 row를 확인한다.
3. 로컬 파일이 `FLOWNOTE_LOCAL_DATA_DIR\Files` 아래 보존됐는지 확인한다.
4. 서버 연결과 계정 권한을 복구한다.
5. 기존 큐를 재시도한다.

같은 파일을 새 제목·새 문서로 다시 올리면 중복 문서가 생길 수 있다.

### 문서 상태·태그 충돌

- 서버 revision과 로컬 기준 revision을 확인한다.
- 태그는 허용된 delta 병합 결과를 검토한다.
- 상태·공개 포인터 충돌은 자동 덮어쓰지 않는다.
- 화면이 제공하는 서버본 유지 또는 새 변경으로 재적용 절차를 사용한다.
- 종결 사유와 담당자를 남긴다.

## 8. Windows 문서 미리보기 실패

1. 문서 형식이 현재 지원 범위인지 확인한다.
2. PDF 미리보기면 WebView2 Runtime 설치와 버전을 확인한다.
3. 원본 파일이 로컬 `Files`에 존재하는지 확인한다.
4. 서버 controlled copy라면 티켓 만료와 SHA-256 결과를 확인한다.
5. 앱을 정상 종료한 뒤 다시 열어본다.

현재 기본 미리보기는 TXT, PDF, XLSX와 이미지를 다룬다. Office/HWP/CAD 전체 렌더링을 지원한다고 가정하지 않는다.

원본 파일을 다른 파일로 덮어쓰거나 DB의 저장 경로를 수동 수정하지 않는다.

## 9. 문서 검토·공개 실패

### 요청할 수 없음

- 문서 작성 권한과 서버 연결을 확인한다.
- 서버 문서 ID와 최신 version이 존재하는지 확인한다.
- 요청 사유, 검토 담당자와 기한을 확인한다.

### 승인·공개할 수 없음

- 현재 역할이 결정 권한을 가지는지 확인한다.
- 요청 때 고정된 version·revision·file hash와 현재 문서가 같은지 확인한다.
- 요청자·검토자·공개자 분리 정책을 확인한다.
- 반려·취소된 요청을 새 공개 요청처럼 재사용하지 않는다.

문서가 바뀌었다면 새 최신 버전으로 검토 요청을 다시 만든다.

## 10. FieldComment 검토 실패

### 독립 결정 차단

적색 또는 상충 기록은 분석자와 결정자가 달라야 할 수 있다. 다른 승인 가능 사용자에게 결정을 요청한다.

### 일괄 처리 부분 성공

1. 결과에서 항목별 성공·실패를 구분한다.
2. 성공 항목의 새 revision과 receipt를 보존한다.
3. 실패 항목의 사유를 수정한다.
4. 실패 항목만 다시 선택한다.

전체 요청이 실패했다고 가정해 성공 항목까지 다시 보내지 않는다.

## 11. 보고서 저장 실패

보고서 저장 전 서버는 원천을 다시 확인한다.

- 서로 다른 원천 유형이 두 종류 이상인지 확인한다.
- FieldComment가 보고서 선정 상태인지 확인한다.
- 공개 문서 버전과 작업순서 revision이 선택 때와 같은지 확인한다.
- 원천 권한이 유지되는지 확인한다.
- 서버 연결이 복구된 뒤 고정 근거를 다시 확인한다.

원천이 바뀌었다면 기존 snapshot을 자동 갱신하지 말고 새 기준으로 다시 선택한다.

## 12. Android 전송 대기·실패

### 전송 대기

새 항목은 자동 전송 대상이다. 로그인과 연결 상태를 확인하고 다음 자동 전송 시각까지 기다린다. `실패 항목 다시 보내기`는 대기 항목을 선택하지 않는다.

### 전송 실패

1. 승인 단말로 로그인돼 있는지 확인한다.
2. 서버 연결과 계정·단말 상태를 확인한다.
3. 마지막 오류 문구를 기록한다.
4. `실패 항목 다시 보내기`를 한 번 누른다.
5. 결과 건수와 남은 실패 건수를 확인한다.

### 부분 성공

- FieldComment 성공·사진 실패: 같은 comment ID로 사진만 재전송한다.
- 인수인계 성공·알림 실패: 같은 handover·message ID로 알림만 재전송한다.
- 후속 FieldComment 성공·알림 실패: 같은 comment ID를 유지한다.

새 입력을 만들어 부분 성공 원천을 복제하지 않는다.

## 13. Android 보안 저장소 오류

### 증상

- 로컬 데이터를 암호화할 수 없음
- 보존된 입력을 열 수 없음
- 보안 저장소 오류로 입력·전송 차단

### 조치

1. 앱 삭제, 데이터 지우기와 단말 초기화를 중단한다.
2. 단말을 네트워크에서 격리할 필요가 있는지 관리자에게 확인한다.
3. Windows에서 단말을 `INACTIVE`로 변경한다.
4. 서버의 원천 ID와 idempotency key 존재 여부를 확인한다.
5. 미전송 자료의 보존·폐기 결정을 승인받는다.
6. 새 device ID로 교체 단말을 등록한다.

Keystore 키를 추출하거나 암호문을 다른 단말에 복사해 복호화하려고 하지 않는다.

## 14. Android 보안 문서 열람 실패

- 문서가 현재 `PUBLISHED`인지 확인한다.
- 사용자 역할과 활성 단말을 확인한다.
- 1회성 grant가 만료·소비됐으면 문서 상세에서 새로 요청한다.
- 수신 파일의 크기·SHA-256 오류가 있으면 부분 파일은 사용하지 않는다.
- PDF 페이지 수나 파일 크기가 서버 한도를 넘는지 확인한다.
- 지원 형식이 PDF, 이미지 또는 UTF-8 TXT인지 확인한다.

파일 앱, 공유 메뉴나 외부 PDF 앱으로 우회 열지 않는다.

## 15. 알림이 오지 않음

1. Android 알림 권한을 확인한다.
2. FlowNote 앱이 강제 중지 상태인지 확인한다.
3. MDM kiosk 재실행 정책과 배터리 최적화 예외를 확인한다.
4. 승인 단말 로그인과 refresh 상태를 확인한다.
5. 서버 알림 cursor와 마지막 message ID를 확인한다.
6. Windows 채널 멤버십과 수신자 지정이 맞는지 확인한다.

관리자만 `알림 위치 초기화`를 검토할 수 있다. cursor를 초기화하면 과거 알림 재표시 범위가 달라질 수 있으므로 원인 확인 없이 사용하지 않는다.

## 16. 서버 복구 뒤 자동 전송 차단

서버 instance, epoch 또는 cursor가 과거로 돌아간 것으로 감지되면 Windows 동기화와 알림 처리가 fail-closed로 멈출 수 있다.

1. 사용자는 재시도를 반복하지 않는다.
2. 서버 운영자는 복구한 DB와 storage가 같은 백업 세트인지 확인한다.
3. 책임 원천 row 수와 fingerprint를 대조한다.
4. Windows `변경 이력`의 서버 재결합 화면에서 이전·현재 manifest를 확인한다.
5. 승인 ID와 담당자를 남기고 업무 재개를 승인한다.
6. 기존 큐와 polling을 재개한다.
7. 유실·중복과 감사 이력을 확인한다.

## 17. 복구 완료 기준

장애가 사라졌다는 화면만으로 완료하지 않는다.

- 원래 업무 원천이 서버 또는 로컬 보존소에 남아 있다.
- 재시도 뒤 같은 공개 ID가 유지된다.
- 중복 문서·FieldComment·인수인계·알림 receipt가 생기지 않았다.
- 서버 read-back이 사용자가 의도한 최종 상태와 같다.
- 실패·충돌·보류 건수가 종결 사유와 함께 정리됐다.
- 장애 원인, 조치, 담당자와 시각이 운영 기록에 남았다.
